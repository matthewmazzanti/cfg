CS2 diagnostic session runbook
==============================

Steam launch options (CS2 > Properties > General > Launch Options — paste as-is):

gamescope -W 3840 -H 2160 -r 60 --force-grab-cursor -f -- gamemoderun env MANGOHUD=1 MANGOHUD_CONFIG=output_folder=/home/mmazzanti/stutter-logs/mangohud,autostart_log=1,log_duration=14400,log_interval=100,font_size=64 %command% -novid +fps_max 240 -condebug -conclearlog

MangoHud settings decoded (headless logger, minimal overlay drawn):
  output_folder=/home/mmazzanti/stutter-logs/mangohud
                          CSV per session lands here. Must be under $HOME and
                          pre-created: cs2 runs inside pressure-vessel, whose
                          /tmp is a private namespace (a container /tmp/mangohud
                          would never reach the host); $HOME is bind-shared at
                          its real path, so host-side memwatch sees the same
                          files. MangoHud does NOT mkdir it (silent fail if
                          missing) — `mkdir -p` it first.
  autostart_log=1         logging starts with the game, no keybind needed
  log_duration=14400      one log covers up to 4h
  log_interval=100        sample every 100 ms instead of every frame (small files)
  font_size=64            overlay text size (default 24; bumped since gamescope
                          renders at 4K internal res, making the default tiny)
memwatch reads the newest CSV in ~/stutter-logs/mangohud for the GAME_FPS column.
Shift_L+F2 toggles logging manually if autostart is ever removed.

(NOT `no_display`: MangoHud #1782 — no_display + autostart_log disables file
logging entirely, not just the overlay. Left off so logging works; the overlay
draws but that's harmless for a diagnostic session.)

(Do NOT use VK_LOADER_LAYERS_ENABLE=VK_LAYER_MESA_overlay instead: forcing the
host Mesa overlay layer into cs2 inside pressure-vessel segfaults the game at
Vulkan init — 3/3 attempts on 2026-07-05. MangoHud is the one layer Valve
supports inside the Steam runtime.)

Experiment queue (ONE knob per session, in order). Overlay-off and KVM-bypass
were eliminated 2026-07-05 (see investigation doc 5.1 / branch 7). Two live:
  [ ] A: single-CCD pin      (prepend `taskset -c 0-5,12-17` to launch options —
                              CCD0 only on the 5900X; isolates cross-CCD sync
                              latency. Affinity is inherited through pressure-vessel.)
  [ ] B: Proton A/B          (Properties > Compatibility > force a Proton version;
                              swaps native Vulkan for D3D11>DXVK>RADV)
Rationale for A-first: the 5900X is the hardest cross-machine constant — same CPU
drove both the RX 580 (Polaris) and the current RDNA3 card, across both stutter
eras. GPU arch changed, CPU didn't. See investigation doc taxonomy 2.4.

Session procedure
-----------------
1. Pre-flight (only after config changes):
     just deploy desktop                  # or `just deploy desktop --build-on-host`
     Reboot IF kernel params/microcode changed; re-login IF groups changed.
     Check:  cat /sys/module/zfs/parameters/zfs_arc_max   -> 8589934592
             sysctl vm.swappiness                          -> 10

2. Set this session's experiment knob (A/B/C above). Note it.

3. Start monitoring (framework):
     mkdir -p ~/stutter-logs/mangohud     # MangoHud won't create it; must pre-exist
     ssh desktop.lan 'python3 -' < scripts/memwatch | tee ~/stutter-logs/$(date +%F)-memlog.txt
   or on the desktop:
     ~/src/nix/cfg/scripts/memwatch | tee ~/stutter-logs/$(date +%F)-memlog.txt

4. Launch the game. Optional sanity checks while in menu:
     gamemoded -s                              # "gamemode is active"
     ps -o pid,ni,comm -C gamescope-wl         # wrapper reniced
   (cs2 itself can never register — pressure-vessel blocks the preload; expected.)

5. During play, drop MARKs the moment anything happens (any terminal):
     echo "stutter start"    > /tmp/memwatch.mark
     echo "map change"       > /tmp/memwatch.mark
     echo "restarted game"   > /tmp/memwatch.mark
     echo "stutter survived restart" > /tmp/memwatch.mark
     echo "stutter gone"     > /tmp/memwatch.mark

6. Optional mid-stutter intervention (tests ZFS branch 3.2, needs sudo on desktop):
     echo $((4*1024*1024*1024)) | sudo tee /sys/module/zfs/parameters/zfs_arc_max
   MARK it. Restore afterwards with 8589934592.

7. After the session, collect:
     ~/stutter-logs/<date>-memlog.txt
     ~/stutter-logs/mangohud/*.csv                   (per-frame FPS/frametime)
     offcpu-clean.txt / offcpu-degraded.txt          (if traced — see below)
     trace.dat (gpuvis), *.rgp / *.rmv               (if captured)
     ~/.local/share/Steam/steamapps/common/Counter-Strike Global Offensive/game/csgo/console.log
     ~/.local/share/Steam/logs/gameoverlayui.log     (overlay sessions)
     ~/.local/share/Steam/logs/console-linux.txt

Tracing the engine stall (behavior-level, not resource-level)
-------------------------------------------------------------
memwatch/MangoHud measure resource LEVELS (all healthy — that's why everything
got eliminated). These tools measure BEHAVIOR: what a thread is blocked on, the
per-frame CPU/GPU/fence timeline, and allocation over time. They can surface
mechanisms not in the taxonomy (lock convoy, allocator slow-path, submission
regression, TLB/IPI storm, DRM fence latency) and are the ONLY tools that can name
what accumulates to the 25-min onset. Run every capture as a pre-onset vs
post-onset DIFFERENTIAL in one session (clean window early, degraded window after
~25 min) — the bug is per-process and resets on restart, so the diff is the signal.

Tools run host-side on the cs2 PID; pressure-vessel is not an obstacle (kernel-side).
Game symbols are stripped, but Mesa/RADV symbols resolve — which is the layer we
suspect.

ONE-SHOT (run ON the desktop, where cs2 is): scripts/stutter-capture fires the
selected probes at the PID into a timestamped ~/stutter-logs/capture-* dir,
skipping any missing tool. nix pulls the toolbox; --command bash -c '...' makes
$PATH expand INSIDE the nix env (single quotes required); `env PATH=` survives
sudo's PATH scrub. Probe tiers: light (default, cheap: offcpu+stat) | flame |
timeline | ccd | full (everything — HEAVY, perturbs the stall). Run it TWICE —
'clean' early, 'degraded' mid-stall — and diff the dirs:

  nix shell nixpkgs#bcc nixpkgs#bpftrace nixpkgs#gpuvis nixpkgs#trace-cmd nixpkgs#linuxPackages.perf \
    --command bash -c 'cd ~/src/nix/cfg && sudo -E env PATH="$PATH" scripts/stutter-capture 20 degraded full'

  # first pass / low observer-effect: swap `full` -> `light`
  # knobs: PERF_CG=dwarf (call stacks), TRACE_HEAVY=1 (sched+irq), PERF_FREQ=999
  # DRY-RUN once in the menu first (10 light, 10 timeline) to shake out tools.

The manual probes below are for follow-up once the one-shot points at a branch.
pid=$(pgrep -x cs2) for those.

1. DECISIVE FIRST TRACE — on-CPU vs off-CPU during a stall (which branch are we on):
     sudo offcputime-bpfcc -p $pid 30 > offcpu-degraded.txt   # + a -clean.txt early
     # quick peek: sudo cat /proc/$pid/task/*/wchan   (kernel func each thread sleeps in)

2. PER-FRAME TIMELINE — gpuvis (Valve's CPU<->GPU<->fence viewer):
     sudo trace-cmd record -e amdgpu -e drm -e gpu_scheduler -e dma_fence \
          -e sched_switch -e irq_vectors sleep 20            # degraded window
     gpuvis trace.dat        # look for the ~40ms hole and which side of the fence

3. DRIVER INTERNALS via Mesa (env vars in the launch line; run MESA_VK_TRACE=help):
     MESA_VK_TRACE=rgp MESA_VK_TRACE_TRIGGER=/tmp/rgp   -> touch /tmp/rgp mid-stall
          (per-frame pipeline/barrier/submission -> open .rgp in Radeon GPU Profiler)
     MESA_VK_TRACE=rmv                                  -> whole-session allocations
          (.rmv in Radeon Memory Visualizer — DIRECT test of "state accumulation":
           watch descriptor/pipeline/alloc counts + working set inflect at onset)

4. CORROBORATION:
     sudo perf record -g -p $pid -- sleep 20     # flame graph; radv_*/ac_* growth = driver
     sudo perf stat -p $pid -e cycles,instructions,stalled-cycles-backend -- sleep 10
          # IPC collapse + backend stalls rising at onset = memory-latency-bound (-> c2c/CCD)
     sudo perf c2c record -p $pid -- sleep 20     # cross-CCD HITM lines (see 2.4)

Result -> interpretation:
  off-CPU futex_wait ................ lock contention (engine or RADV mutex)   [new]
  off-CPU dma_fence_wait, GPU idle .. submission serialization / present stall
  on-CPU, radv_*/ac_* in flame ..... RADV CPU-side work per frame
  on-CPU, backend stalls up, IPC dn . memory-latency-bound -> perf c2c / CCD (2.4)
  high tlb_flush / IPI rate ......... TLB-shootdown storm (CCD-amplified)      [new]
  RMV allocs / working set climb .... engine/driver state ACCUMULATION (core theory)
  gpuvis: growing semaphore/barrier . submission-pattern regression           [new]

What takes effect when (NixOS boot/activation order)
----------------------------------------------------
- nixos-rebuild switch:  sysctls (vm.swappiness), udev rules, packages,
  sudo rules, session variables (new logins), systemd units
- reboot required:       boot.kernelParams (zfs_arc_max), microcode updates,
  kernel/module changes (kvm-amd)
- re-login required:     group membership (gamemode), environment.sessionVariables
